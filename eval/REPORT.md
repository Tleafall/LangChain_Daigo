# 客服 Agent 評估報告

> 這份報告的所有數字都來自 `eval/results/summary.md`，由 `eval/run_eval.py` 自動產生。
> 重跑方式見最後一節。

## 1. 要回答的問題

這個客服 Agent（Gemma 4 E4B，本機 CPU 執行）開發時遇過一個嚴重錯誤：顧客問「有宅配嗎？」，它回答「有提供宅配，運費 60 元」，但店家只有 7-11 取貨付款。當時的修法分兩類：

1. **把規則寫清楚**：FAQ 補上「有宅配嗎？」這題、system prompt 明寫「規則沒寫的服務不能說有」。
2. **能用程式保證的交給程式**：預算內的商品要命中關鍵字才列出、同名商品去重複、門市依「在這條路上／同一區」分組。

當時只用幾個問題、各跑幾次確認。這次要回答的是：

- 這些修改，在一組固定的測試題上，**實際降低了多少捏造、提高了多少答對率**？
- 兩類修法各自貢獻多少？
- 目前版本還有哪些失敗？

## 2. 方法

### 2.1 測試集（`eval/cases.jsonl`，48 題）

| 類別 | 題數 | 測什麼 |
| --- | --- | --- |
| 商品推薦 | 10 | 依需求找商品；其中 3 題有預算（含「預算內根本沒有」的情況） |
| 店家規則 | 12 | 運費、免運、退換貨、付款、未取貨；3 題問宅配／寄到家／寄全家 |
| 門市查詢 | 8 | 用地址找 7-11；3 題故意把行政區講錯（例如學勤路其實在三峽區） |
| 規則外問題 | 11 | 店家規則沒寫的事（刷卡、分期、發票、出貨天數、海外、實體店、點數、禮盒、LINE Pay）和沒賣的商品（SK-II、電視） |
| 多輪追問 | 7 | 「那第一個多少錢」、問完宅配再問全家、先推薦再給預算、運費計算 |

每題寫下判斷規則，例如：

```json
{"id": "S01", "turns": ["我住新北市樹林區學勤路，附近哪家 7-11 可以取貨？"],
 "tools": ["search_711_store"], "must": [["學勤門市", ...], ["三峽"]]}
```

### 2.2 指標

| 指標 | 定義 | 分母 |
| --- | --- | --- |
| **答對率** | 最後一輪回答「包含該有的資訊」而且「沒有違反任何規則」（含沒有捏造）的比例 | 48 題 × 3 seed = 144 筆 |
| **捏造率** | **評分程式偵測到的**捏造比例：本店沒有的服務（宅配、其他超商、刷卡、分期…）、資料裡沒有的金額、本店沒賣的品牌、工具沒給過的門市名稱。偵測器的漏抓率還沒量過，所以 0% 只代表「規則沒抓到」 | 144 筆 |
| **空白回答率** | 最後一則回答是空字串的比例 | 144 筆 |
| **工具正確率** | 最後一輪有呼叫該用的工具（有預算的題目還要檢查 `max_price` 參數填對；地址參數沒有檢查） | 有指定工具的 31 題 × 3 = 93 筆 |
| **回答時間** | 每一輪從送出問題到拿到最終回答的秒數（不含模型第一次載入） | 55 輪 × 3 = 165 輪 |
### 2.3 評分方式：全部用程式判斷

`eval/grader.py` 只用字串比對、正規表示式和數字比對：

- **必須包含**：每一組關鍵字至少出現一個（例如門市題要出現正確的門市名稱）。
- **服務捏造**：肯定句才算，例如「有宅配」算、「沒有宅配」不算（命中位置前 3 個字裡有 不／沒／無／未／非／否，就當成否定句或疑問句排除）。
- **金額捏造**：回答裡的每個「N 元」，必須是資料裡的價格、運費、工具回傳過的數字、顧客說過的數字，或由它們算出的差額（例如「還差 199 元免運」「超出預算 268 元」）。
- **門市捏造**：回答裡列出的門市名稱，必須出現在這段對話的工具回傳裡。
- **預算**：提到超出預算的商品價格時，必須說明「超出」。
- **缺貨**：提到目前缺貨的商品（Kanebo 防曬、MISS DIOR、ZARA），必須說缺貨。
- **指代**：「那第一個多少錢」的回答，必須包含第一輪回答裡第一個商品的價格。

評分規則本身有 29 個自我測試（`eval/test_grader.py`），另外人工檢查了所有判錯的紀錄並抽查判對的紀錄，見 4.4。

讀這張表之前要知道三件事：

1. **答對率要當成上限看。** 抽查 16 筆判對的紀錄，有 2 筆其實有問題（見 4.4）。
2. **「0 筆捏造」只代表評分規則沒抓到。** 偵測器的漏抓率還沒量過。

### 3.2 差距是否超過隨機變動（以題為單位的配對比較）

同一題的 3 個 seed 結果高度相關（三種設定只有 16 題分數不同），所以不能把 144 筆當成 144 個獨立樣本。這裡把每題 3 次的答對數當成一個樣本，有效樣本是 48 題：

| 比較 | 答對率差 | 95% 信賴區間（bootstrap） | 變好題數 | 變差題數 | 符號檢定 p | 有捏造的題數 |
| --- | --- | --- | --- | --- | --- | --- |
| A → B | +6.9pp | [−2.8, +17.4] | 9 | 5 | 0.42 | 3 → 0 |
| B → C | +0.0pp | [−2.8, +2.8] | 2 | 2 | 1.00 | 0 → 0 |
| A → C | +6.9pp | [−3.5, +18.1] | 10 | 5 | 0.30 | 3 → 0 |

**結論：三組比較的答對率差距都不顯著。** A → B 的方向是變好，但信賴區間包含 0；「有捏造的題數」從 3 題變成 0 題，題數太少，也無法排除隨機（3 題全部朝同一方向的機率，在沒有差別時是 1/4）。這張表由 `run_eval.py` 自動產生，見 `eval/results/summary.md`。

（舊版報告寫過「各 seed 答對率區間沒有重疊」，那是把 3 個 seed 當成獨立樣本，說法太強，已經改成這張表。）

### 3.5 解讀

**A → B（寫清楚規則）：在問服務的題目上方向一致，但樣本太少，不能說是顯著的改善。**
A 偵測到的 5 筆捏造全部出在「本店沒有的服務」，分布在 3 題：寄全家 3 筆、宅配 1 筆、刷卡 1 筆。A 被問「有宅配嗎」時，3 次裡 1 次說「有提供宅配」、2 次只回答運費而不正面回答；被問「可以寄全家嗎」，3 次都以「可以喔！」開頭。B 加上 FAQ 宅配題和 prompt 規則後，問服務和付款的 6 題（F06、F10、F11、F12、O01、M02）3 次全部答對，而且這 6 題沒有一題變差。

能說的是：在這組題目上，原本出錯的宅配類問題在 B 都答對了，A 的失敗也正好重現了當初的真實錯誤。不能說的是：「寫規則讓捏造率顯著下降」。有捏造的只有 3 題（3 → 0），配對檢定無法排除隨機（見 3.2）。另外，A 是拿掉 FAQ 宅配題還原出來的，所以宅配題的改善有一部分是「把答案放回知識庫」的直接結果；刷卡那 1 筆和 FAQ 無關，對應的是被拿掉的 prompt 規則。

**A → B 的代價：商品推薦類從 90.0% 降到 70.0%。**
主要來自 P03「我想找洗髮精」：B 三次都沒有查商品，而是反問「需要哪一類型的洗髮精」（A 三次都直接列出 3 款）。反問本身不算錯，但顧客沒拿到任何商品，評分規則把它算答錯，工具正確率的 96.8% 也全是這 3 筆。B 和 A 的差別只有 4 段 prompt 和 1 題 FAQ（見 2.4），這次沒有逐段拿掉測試，所以**不能確定是哪一段造成反問**。這和上一段的改善放在一起看，像是一種取捨：規則讓模型更保守，比較不會亂說，但也比較不會直接去查。這只是一個題目上的觀察，要確認需要更多同類題目。P02、P04 在 A 也有一部分失敗，見 4.2。

**B → C（交給程式）：整體答對率相同（85.4%），差在失敗的型態。**
- 空白回答從 4 筆降到 1 筆，S04、S08 因此從 2/3 變成 3/3。
- 門市「行政區講錯」的題目沒有變好，S07 從 1/3 變成 0/3、S03 從 2/3 變成 1/3。C 的工具會把門市分成「【最推薦：在這條路上】」和「【顧客說的區的其他門市】」兩組，並寫明「回答時一定要列出這一組」，但模型常常只列第二組（見 4.1）。
- 以題為單位，B → C 是 2 題變好、2 題變差（見 3.2），**和隨機變動無法區分**。能說的只有：程式邏輯的修改在這組題目上沒有帶來可測到的整體差異。

## 4. 失敗案例分析

以下引用的回答都可以在 `eval/results/raw/` 找到原文。

### 4.1 目前版本漏列「最符合的門市」（S01、S07，C 都是 0/3）

顧客說「我住新北市樹林區學勤路」，工具回傳：

```
提醒：「學勤路」上的 7-11 在三峽區，不在顧客說的樹林區，請跟顧客確認地址。
【最推薦：在「學勤路」上的門市】（回答時一定要列出這一組）
- 學勤門市（店號 281766）：新北市三峽區學勤路105號…
【樹林區的其他門市】
- TBI門市 … 三暉門市 … 千歲門市 …
```

C 三次都有說「學勤路的 7-11 在三峽區」，但接著只列出樹林區的三家，沒有列學勤門市。S07（士林區光復南路）也一樣：只列士林區的門市，沒有列光復南路上的。

可能的原因是顧客明確說了「我住樹林區」，模型把「顧客說的區」看得比工具裡的指示更重要。這代表**把指示寫在工具回傳裡，不能保證小模型照做**。如果要保證，下一步應該在程式端處理（例如行政區不符時，工具只回傳路名符合的門市，或由程式直接組出回答的第一行），而不是再加強文字。

### 4.2 推薦了不相關的商品（P02、P04）

- P04「有沒有香水？想送女朋友」：B、C 三次都推薦了「TOMICA 中華郵政郵務車」（玩具車），A 也有 2 次。
- P02「想買卸妝的產品」：B、C 三次都推薦了「瑪琍嘉蘭 護理霜」，C 還補了一句「雖然是保養品…可以參考」。

商品搜尋是語意向量搜尋，「送禮」「卸妝」會撈到語意相近但類別不對的商品，模型照單全收。C 加的「預算內要命中關鍵字」只在有預算時生效，這兩題沒有預算，所以 B、C 結果一樣。

### 4.3 反向捏造：規則沒寫的事，說成「沒有」（O03）

「有開發票嗎？可以打統編嗎？」店家規則沒有寫，正確做法是請顧客問真人客服。B、C 在 seed1 這樣回答，但 seed2、seed3 都說「我們目前不提供開發票或打統編的服務喔」。

這和「編造宅配」是同一種錯，只是方向相反：坑 6 的規則是「規則沒寫的服務不能說有」，沒有限制「不能說沒有」。這次的評分把它算答錯，但沒有算進捏造率（捏造率只抓肯定句），所以**捏造率 0% 不代表不會亂講**。

### 4.4 評分規則的人工檢查

規則是字面比對，一定有誤判，所以每一輪結果出來都人工看過。

**檢查方式**：讀過所有被判錯的紀錄，並從被判對的紀錄抽查。

**第一次（只看 A 的結果，還沒看到 B、C）**，修正：
- 否定句判斷原本只看前 1 個字，「目前沒有提供分期」會被判成捏造，改成看前 3 個字。
- 「請在結帳頁面搜尋門市」被當成店名，改成只檢查列表、粗體這類店名的位置。
- S07 的「光復南」同時是路名，會讓沒列門市的回答被判對，改成要求店名。
- P04 推薦玩具車、P02 推薦護理霜原本被判對，加上「不該出現」。
- F12 以「可以喔！」開頭（說可以寄全家）原本被判對，加上「開頭說可以就算捏造」。
- 新增「空白回答」的判斷。

**第二次（看完 B、C 的結果）**，又找到 5 種把正確回答判錯的情況：

| 回答 | 原本 | 修正 |
| --- | --- | --- |
| 「本店只透過統一超商賣貨便寄送到 7-11 門市」（問能不能寄全家） | 缺少「不能／沒有」 | 接受「只透過／只有」 |
| 「我們目前只有 7-11 賣貨便取貨付款這一種取貨方式」（問寄到家） | 缺少「不能／沒有」 | 同上 |
| 「店家的規則中沒有提到是否可以開發票…請洽真人客服」 | 「可以開發票」判成捏造 | 「是否」視為疑問 |
| 「以下是相關門市清單」 | 「以下是相關門市」判成假店名 | 「相關」列為一般字詞 |
| 「768 元，比您的預算高出 268 元」 | 沒有說明超出預算 | 接受「高出」 |

這 5 種修正一共改變了 13 筆紀錄的判斷（B 6 筆、C 7 筆），全部是「判錯 → 判對」。修正前 B、C 的答對率是 81.2%、80.6%，捏造率 0.7%、1.4%。A 的分數不受影響（A 沒有出現這些說法）。

**這個流程的問題要說清楚**：第二次修正是在看過 B、C 的結果之後做的，等於評分規則被結果影響過。我的處理方式是：
1. 只修「明顯把正確回答判錯」的情況，每一項都附上原文。
2. 修改後三種設定都用同一套規則重新評分（`--regrade`）。
3. 修正前後的數字都寫在這裡。

**抽查判對的紀錄**：從 B、C 判對的紀錄隨機抽 16 筆，2 筆其實有問題但被判對：
- C seed1 P10「油痘肌適合用什麼」推薦了一款洗髮精（語意錯誤，規則只檢查有沒有提到合理的候選商品）。
- C seed2 M04 把同一款 Kanebo 防曬列了兩次。原因是資料裡同一款商品上架了兩次，標題差了一個「NT$195」，C 的「同名去重複」是比對完整名稱，所以沒擋到。這是目前版本的一個真實 bug。

16 筆太少，不能拿來換算真正的答對率（2/16 的 95% 區間大約是 2%～38%），但足以說明判對的紀錄裡確實有漏判，**答對率應該當成上限來看**。

## 5. 限制

1. **A 是還原的**，不是當時的程式碼（見 6 的說明）。A 的分數可能和當時真實的版本不同。
2. **題數少**。有效樣本是 48 題，不是 144 筆：同一題的 3 個 seed 高度相關。以題為單位的配對比較，三組比較的答對率差距都不顯著（見 3.2），單一類別（7～12 題）的差距更不能下結論。
3. **捏造偵測器的漏抓率沒量過**。人工只檢查了判錯的紀錄，並抽查判對的紀錄；「判定沒有捏造」的紀錄沒有系統性地抽查。否定句判斷只看前 3 個字，像「不過也有宅配喔」這種句子，會因為前面的「不過」被當成否定句而漏抓（已實測）。
4. **3 個 seed 不等於 3 個顧客**。seed 只改變取樣隨機性，題目的問法是固定的。真實顧客的問法更多樣（錯字、一次問很多件事），這組題目沒有涵蓋。
5. **題目和評分規則都是我寫的**，而且我知道這個 Agent 過去在哪裡出錯，題目會偏向那些地方（這也是刻意的，見 6）。數字只代表「在這 48 題上」的表現。
6. **評分規則看過結果後修改過兩次**（見 4.4）。
7. **語意判斷做不到**：推薦的商品適不適合、回答是否答非所問，規則只能部分檢查（抽查 16 筆有 2 筆漏判）。
8. **只有一個模型、一台電腦**。換成較大的模型，A 和 B 的差距可能會縮小；換電腦或換 Ollama 版本，回答也可能不同。

## 6. 設計決策（為什麼這樣設計）

這一節記錄每個選擇的理由和放棄的替代方案，方便日後說明。

**為什麼是 48 題，而不是幾百題？**
每題在 CPU 上要 5～40 秒，三種設定 × 3 次就是 432 次對話、約 2～3 小時。48 題足以讓每個類別有 7～12 題，看得出類別之間的差異；再多就跑不動，也會讓人工檢查變得不可能。代價是信賴區間很寬：一題就是 2 個百分點，所以報告裡只解讀差距明顯的結果。

**為什麼測試集要刻意放「規則外」和「行政區講錯」的題目？**
真實出過的錯（編造宅配、漏列最符合的門市）都發生在「資料沒寫」或「顧客講錯」的時候。如果測試集只有資料裡查得到的正常問題，分數會很好看，但測不到真正的風險。11 題規則外問題佔了 23%，是刻意的比例。

**為什麼把「捏造率」和「答對率」分開？**
對客服來說，兩種錯的代價不同。「沒答到重點」顧客會再問一次；「自信地說有宅配」顧客會照著做然後出問題。分開算才看得出一個修改是「讓回答更完整」還是「讓它不亂講」。捏造的回答一定算答錯，但答錯不一定是捏造。

**為什麼全部用程式評分，不用 LLM 當裁判？**
1. 可重現：同樣的回答永遠得到同樣的分數，改了規則可以用 `--regrade` 對舊回答重新評分，不用重跑模型。
2. 這個任務大部分「對錯」本來就能用程式判斷：價格對不對、門市名稱是不是工具給的、有沒有說「沒有宅配」。
3. 能用的裁判只有本機的 Gemma 4 E4B，也就是被評估的同一個小模型，它自己會犯的錯（把「運費 60 元」推論成宅配），當裁判時也可能看不出來；用付費 API 當裁判，則違背了這個專案「完全免費、資料不出本機」的前提。
代價：規則是字面比對，會有誤判（見 4.4 的人工檢查），而且「推薦的商品適不適合這個膚質」這類語意判斷做不到，只能檢查「有沒有推薦到合理的候選商品之一」。

**為什麼要固定 seed？**
temperature 0.2 仍然有隨機性。固定 seed 讓「同一台電腦重跑得到一樣的數字」，報告裡每個數字都能被別人驗證；跑 3 個不同 seed，則是用來看隨機性造成的變動有多大，避免把運氣當成改善。

**為什麼要比較三種設定，而不是只報目前版本的分數？**
單一個分數（例如「答對率 80%」）沒有參考點，看不出好壞。和早期版比，才能說「修改帶來了多少改善」；中間多一個 B，才能把「寫規則」和「交給程式」兩種修法的效果分開。

**為什麼早期版是「還原」的，這樣可信嗎？**
這是這份評估最大的弱點，所以寫在最前面的方法裡。還原的依據是踩雷紀錄裡逐項寫下的修改內容，每一段拿掉的 prompt 都用 assert 確認存在於目前版本、可以逐行對照。有兩點可能和當時不同：門市「行政區不符」的提醒，當時是否已經存在不確定，這裡保守地保留（會讓 A 看起來比實際好）；其他坑 1～5 的修正都保留。

**為什麼「工具正確率」只算 31 題？**
規則外問題（例如「可以刷卡嗎」）不一定需要工具：模型可以直接依 prompt 回答「只能取貨付款」，也可以查 FAQ。硬性規定某個工具，會把合理的回答算成錯。

## 7. 怎麼重現

```powershell
.\.venv\Scripts\python.exe eval\test_grader.py                         # 評分規則自我測試
ollama stop gemma4:e4b                                                  # 16GB 記憶體時先釋放記憶體
.\.venv\Scripts\python.exe eval\run_eval.py --variants all --repeats 3  # 約 2～3 小時
.\.venv\Scripts\python.exe eval\run_eval.py --regrade                   # 只重新評分
```

原始紀錄已經附在 `eval/results/raw/`，不跑模型也可以用 `--regrade` 驗證每一個數字。換電腦、換 Ollama 版本，回答可能不同（seed 只保證同一個環境可重現）。
