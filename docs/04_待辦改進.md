## 1. 商品文字清理：拿掉 emoji、重要資訊放前面

### 為什麼要改（2026-11-12 實測）

| 項目 | 數據 |
| --- | --- |
| Embeddings 模型一次能讀的長度 | 128 個 token，超過的部分直接截掉 |
| 每個商品的文字長度 | 中位數 357 個 token，最長 674 |
| 超過 128 的商品 | **63 個裡有 62 個** |
| 有 emoji 的商品 | 63 個裡有 62 個 |
| 每個商品的 emoji 數量 | 中位數 17 個，最多 37 個 |

- 模型平均只讀到商品文字的前三分之一，後面的成分、適合膚質、使用方式都看不到。
- 每個 emoji 佔一個 token（前後常再多一個空白 token），17 個 emoji 大約吃掉 128 個位置裡的 20～30 個。
- 範例：「✨慶開幕✨ 🌹 告別熬夜疲憊肌！」被切成 `✨ / 慶 / 開幕 / ✨ / 🌹 / 告 / 別 / 熬 / 夜 …`。
- 這也是之前搜「卸妝」時，卸妝液在意思搜尋只排第 20 名的原因之一。

### 做法

**只清理「拿去轉向量的文字」**。原始資料（`products.json`）和給 Gemma 看的內容（工具回傳）都保留原樣。

1. 寫一個 `clean_for_embedding(text)` 函式：
   - 拿掉 emoji（Unicode 範圍 `U+1F000–U+1FAFF`、`U+2600–U+27BF`、`U+2B00–U+2BFF`、`U+FE0F`、`U+200D`）。
   - 拿掉常見行銷用語：「慶開幕」、「手刀」、「趕快」、「數量有限」、「不搶對不起自己」等（清單放在程式裡，方便增減）。
   - 把連續的空白、換行壓成一個空白。
2. 重新安排向量文字的順序，**重要的放前面**，被截掉的只會是比較不重要的部分：
   `商品名稱 → 分類 → 規格 → 說明的前段`
3. 混合搜尋的關鍵字比對（`_bigrams`）也改用清理後的文字。

### 要改的檔案

- `src/knowledge.py`：新增 `clean_for_embedding`，修改 `build_product_store`。

### 怎麼驗證（不要憑感覺）

1. 先寫一份測試題 `tests/product_search_cases.json`，15～20 題，每題標好正確商品。例如：

   | 問題 | 正確答案應該包含 |
   | --- | --- |
   | 卸妝 | 妮頓絲重點卸妝液、雪肌精淨透潔顏油 |
   | 乾肌保濕 | JYUNKA 玻尿酸面膜、瑪琍嘉蘭 240 號保濕精華 |
   | 防曬 | Kanebo 防曬水凝乳、倩碧 UV 隔離乳 |
   | 洗髮精 | FIG 洗髮精、Dr. Groot 洗髮精 |
   | 香水 | Miss Dior、蘭蔻唯我淡香水 |

2. 寫一支小程式算 **Recall@3**（正確商品有沒有出現在前 3 名）。
3. **改之前先跑一次記下分數**，改完再跑一次比較。分數有變好才保留。
4. **順便找出最好的 `keyword_weight`**：目前的 0.3 是依經驗設的，沒有系統性調整過。用同一份測試題，分別試 0、0.1、0.2、0.3、0.5、1.0，各算一次 Recall@3，選分數最高的（分數差不多時選小一點的，避免關鍵字壓過意思）。
5. 再跑一次 `run_demo.bat`，確認客服回答正常。

## 2. 門市比對：比對「段」和門牌號碼

### 為什麼要改（2026-11-12 實測）

| 顧客地址 | 結果 | 問題 |
| --- | --- | --- |
| 新北市三峽區學勤路100號（虛構地址） | ✅ 學勤門市 | — |
| 台北市大安區復興南路一段247號 | ✅ 大安復興門市 | 剛好資料順序對 |
| 台北市大安區復興南路**二段**100號5樓 | ❌ 列出 3 家都在一段 | 「段」被忽略 |
| 桃園市中壢區中正路**100巷**20號 | ⚠️ 列出 1262 號、四段、三段 | 門牌號碼被忽略，離很遠 |
| 台中市西屯區台灣大道**三段99號** | ⚠️ 第一家在二段 938 號 | 「段」和號碼都被忽略 |
| 新北市樹林區**樹福里**復興路30號 | ⚠️ 路名被抓成「樹福里復興路」 | 「里」被當成路名；門市地址沒寫里就會找不到 |
| 高雄市前鎮區中山二路2號 | ⚠️ 提醒「中山二路的 7-11 在苓雅區，不在前鎮區」 | 中山二路其實也經過前鎮區，提醒會讓顧客以為地址寫錯 |

### 做法一（先做）：用地址文字推估，不需要外部服務

1. **先去掉「里」、「鄰」**：例如「樹福里」、「5鄰」，再抓路名。
2. **解析「段」**：一段、二段、三段……（也要處理「2段」這種數字寫法）。同一條路，同一段的門市排前面。
3. **解析門牌號碼**：「100巷20號」取 100、「247號」取 247。同一條路同一段，用號碼差距由小到大排序。
4. **改提醒的說法**：
   - 舊：「學勤路上的 7-11 在三峽區，不在顧客說的樹林區，請跟顧客確認地址」
   - 新：「顧客說的樹林區，在學勤路上沒有 7-11；這條路上的門市在三峽區。可以請顧客確認地址，或選擇同區的其他門市」
5. 解析結果多回傳 `section`（段）和 `number`（號），方便除錯。

限制：門牌號碼接近不代表實際距離近（路的對面、轉角後的另一條路）。

### 做法二（之後再考慮）：用經緯度算真正距離

- **門市座標已確認拿得到**：7-11 官方電子地圖 API（`emap.pcsc.com.tw/EMapSDK.aspx`）每家門市都有 `<X>`、`<Y>`。例如三角湧門市 `X=121365766`、`Y=24914440`，就是經度 121.365766、緯度 24.914440。目前 `D:\Project002\scripts\fetch-711-stores.mjs` 沒有把它存下來，只要加兩個欄位就好。
- **顧客地址轉座標**：需要地理編碼服務，例如 Google Maps Geocoding API（付費）或政府 TGOS（要申請）。顧客地址會傳給該服務，要注意隱私。
- 算直線距離，列出最近的 3 家。

### 要改的檔案

- `src/knowledge.py`：`search_stores`（做法一）。
- `src/step5_agent.py`：`search_711_store` 的提醒文字。
- 做法二另外要改 `D:\Project002\scripts\fetch-711-stores.mjs`（存 X、Y），以及新增地理編碼。

## 3. 向量庫存檔：建一次，之後直接讀取

### 為什麼要改

目前用 `InMemoryVectorStore`，只存在記憶體，每次啟動都重新把 82 段文字（19 題 FAQ＋63 個商品）轉成向量。

能省的時間有限（以下是粗估）：

| 啟動時做的事 | 大約時間 | 存檔後能省掉嗎 |
| --- | --- | --- |
| 載入 Python 套件 | 約 10 秒 | 不能 |
| 載入 Embeddings 模型 | 約 15 秒 | **不能**（每個問題都要先轉成向量才能比對） |
| 把 82 段文字轉成向量 | 約 10 秒 | 可以 |

現在資料少，大約省 10 秒；資料變多（幾千個商品）以後就很重要。

### 做法

1. 用 `InMemoryVectorStore` 內建的 `dump(path)` 存檔、`InMemoryVectorStore.load(path, embeddings)` 讀檔。存在 `data/cache/`。
2. **資料有變才重建**：把 `faq.md`、`products.json` 的內容算一個雜湊值（hash），連同向量庫一起存。
   - 啟動時雜湊值一樣 → 直接讀檔。
   - 雜湊值不一樣（剛同步過）→ 重建並存檔。
   - 清理文字的規則（第 1 項）或 Embeddings 模型改了，也要重建，所以雜湊值也要包含這些設定。
3. `data/cache/` 被刪掉也沒關係，下次啟動會自動重建。

### 要改的檔案

- `src/knowledge.py`：`build_faq_store`、`build_product_store` 外面包一層「有快取就讀、沒有就建」。

### 怎麼驗證

1. 第一次啟動：顯示「建立向量庫並存檔」，記下時間。
2. 第二次啟動：顯示「讀取已存的向量庫」，應該比第一次快。
3. 執行 `sync_data.bat` 後再啟動：應該顯示「資料有更新，重新建立」。
4. 跑 `run_demo.bat`，結果跟改之前一樣。

## 4. 推薦缺貨商品時要說明

### 為什麼要改

之前測試「乾燥肌男士 500 元」時，推薦了缺貨的神經醯胺滋潤乳霜，回答裡沒提到缺貨。工具其實有回傳「目前缺貨」，是模型沒講。

### 做法

- `src/step5_agent.py` 的 `SYSTEM_PROMPT`「推薦商品的規則」加一條：「推薦缺貨的商品時，一定要說明目前缺貨。」
- 或在工具裡直接把缺貨商品排到最後（能用程式保證的就用程式）。

### 怎麼驗證

問「有沒有適合乾肌的保濕產品？」，有缺貨商品出現時，回答要提到缺貨。
