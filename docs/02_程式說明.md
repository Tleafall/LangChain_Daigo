# 02 程式說明：每一步在做什麼

這份文件一支一支解釋 `src/` 裡的範例程式。建議照順序看，每一步都建立在前一步上。

每一節的格式：
- **這一步的目標**：做完會得到什麼
- **執行方式**
- **程式解說**：一段一段看
- **預期結果**：正常的輸出長什麼樣子
- **動手改改看**：小練習

---

## 共用設定：config.py

所有範例程式都從這裡拿模型，**想換模型只要改這個檔案**。

```python
MODEL_NAME = "gemma4:e4b"
EMBEDDING_MODEL = "sentence-transformers/paraphrase-multilingual-mpnet-base-v2"

def get_model(temperature=0.2):
    return ChatOllama(model=MODEL_NAME, temperature=temperature, reasoning=False)
```

| 設定 | 意思 |
| --- | --- |
| `MODEL_NAME` | 要用 Ollama 裡的哪個模型，要先 `ollama pull` 下載 |
| `EMBEDDING_MODEL` | 把文字轉成向量的模型，支援中文，第一次用會自動下載 |
| `ChatOllama` | LangChain 連接 Ollama 的「轉接頭」 |
| `temperature` | 0～1，越低回答越穩定一致，越高越有變化。客服適合低一點 |
| `reasoning=False` | 關掉 Gemma 4 的「思考模式」。開著會比較聰明但慢很多，CPU 電腦建議關掉 |
| `USE_GPU` / `num_gpu=0` | `False` 時強制只用 CPU。**AMD 顯卡在 Windows 上實測會讓 Ollama 當掉**（見下方說明），所以預設關掉。有 NVIDIA 顯卡可以改成 `True` |

> **為什麼預設不用 GPU？** 開發這個專案的電腦是 AMD RX 5600M 顯卡。Ollama 嘗試用顯卡跑 Gemma 4 時，出現 `ErrorOutOfHostMemory` 錯誤，模型直接載入失敗。加上 `num_gpu=0` 強制用 CPU 以後就正常了，而且載入後一題只要幾秒。

> **這就是 LangChain 的好處**：如果之後要換成 Claude，只要把 `ChatOllama(...)` 換成 `ChatAnthropic(...)`，其他程式完全不用改。

還有一行 `sys.stdout.reconfigure(encoding="utf-8")`：Windows 終端機預設不是 UTF-8，印中文可能變亂碼，這行統一處理掉。

## 步驟 1：step1_hello.py —— 跟 AI 說第一句話

### 這一步的目標
確認環境裝好了，並學會最基本的三件事：建立模型、送出問題、拿出答案。

### 執行方式
```powershell
python src\step1_hello.py
```

### 程式解說

**第 1 部分：最簡單的發問**

```python
model = get_model()
answer = model.invoke("用一句話介紹你自己")
print(answer.content)
```

- `invoke`：英文「呼叫」，就是「送出問題，等它回答」。
- 回傳的 `answer` 不是文字，是一個 `AIMessage` 物件（像一個包裹），裡面除了文字還有其他資訊。
- `.content`：把包裹裡的文字拿出來。

**第 2 部分：加上角色**

```python
messages = [
    SystemMessage(content="你是一位代購店的親切客服，回答要簡短，用繁體中文。"),
    HumanMessage(content="你們店是賣什麼的？"),
]
answer = model.invoke(messages)
```

| 訊息類型 | 誰說的 | 用途 |
| --- | --- | --- |
| `SystemMessage` | 開發者 | 設定 AI 的身分和規則，使用者看不到 |
| `HumanMessage` | 使用者 | 使用者的問題 |
| `AIMessage` | AI | AI 的回答 |

**第 3 部分：看看包裹裡還有什麼**

```python
print(answer.usage_metadata)
```

會印出用了多少 token。本機模型不用錢，但換成付費模型時，這就是計費的依據。

### 預期結果
- 第 1 部分：AI 用一句話自我介紹，並顯示花了幾秒。
- 第 2 部分：AI 用客服的口吻回答（它不知道店裡真的賣什麼，所以會講得很籠統，這很正常，到步驟 4 才會給它資料）。
- 第 3 部分：顯示 `AIMessage` 和 token 用量。

### 動手改改看
1. 把 SystemMessage 改成「你是一位講話很像海盜的客服」，看回答怎麼變。
2. 把 `get_model()` 改成 `get_model(temperature=0.9)`，同一個問題問三次，看回答是不是每次都不一樣。

## 步驟 2：step2_chain.py —— 模板 + 管線

### 這一步的目標
學會用模板（不用每次重打指令）和管線 `|`（把步驟串起來）。

### 執行方式
```powershell
python src\step2_chain.py
```

### 程式解說

**三個站**

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一位{role}，用繁體中文回答，不超過三句話。"),
    ("human", "{question}"),
])
model = get_model()
parser = StrOutputParser()
```

| 站 | 比喻 | 輸入 → 輸出 |
| --- | --- | --- |
| `prompt` | 填空題 | 字典 `{"role": ..., "question": ...}` → 填好的訊息 |
| `model` | 廚師 | 訊息 → `AIMessage` 包裹 |
| `parser` | 拆包裹 | `AIMessage` → 純文字 |

`{role}` 和 `{question}` 是空格，呼叫時用字典填進去。

**用 `|` 串起來**

```python
chain = prompt | model | parser
chain.invoke({"role": "代購店的親切客服", "question": "我第一次網購，要注意什麼？"})
```

`|` 的意思：**前一站的輸出，就是下一站的輸入。** 串好的 `chain` 本身也能用 `.invoke()` 啟動。

**小實驗：只跑其中一站**

```python
print(prompt.invoke({"role": "客服", "question": "測試"}))
```

每一站都能單獨執行。除錯時很好用：哪一站結果怪怪的，就單獨跑那一站看看。

### 預期結果
同一個問題，「親切客服」和「嚴肅的消費者保護專家」會用完全不同的語氣回答。最後印出模板填好以後的樣子。

### 動手改改看
1. 在 `for role in [...]` 裡加一個新身分，例如「熱情的直播主」。
2. 把模板改成三個空格，多一個 `{style}`（例如「條列式」或「一段話」）。

## 步驟 3：step3_tool_test.py —— 測試模型會不會用工具

### 這一步的目標
做 Agent 之前，先確認這個模型**會正確呼叫工具**。小模型常常不用工具就自己編答案。

### 執行方式
```powershell
python src\step3_tool_test.py
```

### 程式解說

**定義工具**

```python
@tool
def get_price(product_name: str) -> str:
    """查詢商品目前的售價。只要顧客問到價格，一定要用這個工具查。"""
    return f"{product_name} 目前售價 680 元"
```

- `@tool`：把一般的 Python 函式變成 AI 可以使用的工具。
- `product_name: str`：參數的型別，AI 會照這個格式傳參數進來。
- **docstring（三個引號裡的說明）最重要**：AI 看不到你的程式碼，**只看這段說明**來決定要不要用這個工具、怎麼用。
- 這裡回傳固定的 680 元，是故意的：如果 AI 最後回答 680，就證明它真的用了工具；如果回答別的數字，就是它自己編的。

**組成 Agent**

```python
agent = create_agent(
    model=get_model(),
    tools=[get_price],
    system_prompt=(
        "你是代購店的客服，用繁體中文回答。\n"
        "顧客問價格時，直接把顧客說的商品名稱當作參數，呼叫 get_price 查詢，不要先反問顧客。\n"
        "價格一定要用工具查，不能自己猜。"
    ),
)
```

> **實測故事：多一句話，結果完全不同**
> 一開始 system prompt 只寫「價格一定要用工具查，不能自己猜」。Gemma 4 沒有用工具，而是反問顧客：「請問您指的是哪一款保濕乳液呢？」
> 它沒有亂編，只是太客氣了。加上「直接把顧客說的商品名稱當作參數，不要先反問顧客」這一句以後，連續跑 3 次都正確呼叫工具。
> **教學重點：小模型需要你把「該怎麼做」講得非常具體。**

**看 Agent 的每一步**

```python
result = agent.invoke({"messages": [{"role": "user", "content": question}]})
for m in result["messages"]:
    ...
```

`result["messages"]` 是整段對話紀錄。一次成功的工具呼叫，會看到這四則訊息：

| 順序 | 訊息類型 | 內容 |
| --- | --- | --- |
| 1 | `HumanMessage` | 顧客的問題 |
| 2 | `AIMessage`（帶 `tool_calls`） | AI 決定：「我要呼叫 get_price，參數是保濕乳液」 |
| 3 | `ToolMessage` | LangChain 執行工具，把結果「680 元」送回去 |
| 4 | `AIMessage` | AI 根據 680 元寫出最後回答 |

**重點：第 2 步 AI 只是「說」要用工具，真正執行函式的是 LangChain（第 3 步）。**

### 預期結果
畫面會出現 `>>> [工具被呼叫了]`，最後顯示「通過」。

如果顯示「沒通過」：
1. 再跑一次（小模型有時候會不穩定）。
2. 更新 Ollama 和套件：`pip install -U langchain langchain-ollama`
3. 換大一點的模型（`config.py` 改成 `gemma4:12b`）。

### 動手改改看
1. 把 docstring 改成很隨便的「價格」兩個字，跑幾次看看，AI 還會不會用工具？
2. 再加一個工具 `get_stock(product_name)` 查庫存，問「保濕乳液多少錢、還有貨嗎？」，看 AI 會不會兩個工具都用。

## 步驟 4：step4_rag_faq.py —— RAG，先查 FAQ 再回答

### 這一步的目標
讓 AI 根據店家的 FAQ 回答問題，而不是自己亂猜。

### 執行方式
```powershell
python src\step4_rag_faq.py
```

> 第一次執行會下載 Embeddings 模型（約 1 GB），請耐心等。

### 整體流程

```
【事前準備，只做一次】
faq.md → 依「## 」切成一題一段 → 轉成向量 → 存進向量資料庫

【每次提問】
問題 ─┬─ context 路：去資料庫找最像的 2 段 → 合成一段文字
      └─ question 路：問題原封不動傳下去
              ↓
       填進模板 → Gemma 4 回答
```

### 程式解說

**1. 切段**

```python
splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[("##", "question")])
chunks = splitter.split_text(faq_text)
```

FAQ 本來就是一題一題的，所以用「## 」當切點，剛好一題一段。切完每段的 `metadata["question"]` 會記住它的標題。

接著把問題也放進內文（`問：...\n答：...`），這樣搜尋時，問題的文字也會被比對到，比較容易找準。

**2. 轉成向量、存進資料庫**

```python
embeddings = HuggingFaceEmbeddings(
    model_name=EMBEDDING_MODEL,
    encode_kwargs={"normalize_embeddings": True},
)
store = InMemoryVectorStore.from_documents(chunks, embeddings)
```

- Embeddings 模型把每一段文字轉成一串數字（向量），**意思越接近的文字，向量越接近**。
- `normalize_embeddings=True`：把向量長度統一成 1。這樣餘弦相似度最準，也跟模型訓練時的方式一致。
- `InMemoryVectorStore`：存在記憶體裡的向量資料庫，預設用**餘弦相似度**比較，程式關掉就消失，練習剛好。

**3. 搜尋測試**

```python
store.similarity_search_with_score("東西壞掉可以換嗎", k=3)
```

會印出最像的 3 題和相似度分數（越接近 1 越像）。注意問題裡沒有「瑕疵」兩個字，還是能找到「商品有瑕疵怎麼辦」，因為比的是**意思**不是字面。

**4. 組成 RAG Chain（那個字典）**

```python
rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | get_model()
    | StrOutputParser()
)
```

| 部分 | 做什麼 |
| --- | --- |
| `retriever` | 拿問題去資料庫找最像的 2 段，回傳 `Document` 清單 |
| `format_docs` | 把好幾個 `Document` 的文字抽出來，用空行接成一整段 |
| `RunnablePassthrough()` | 什麼都不做，把問題原樣傳下去 |
| 整個字典 | 同一個問題同時走兩條路，結果合成 `{"context": 資料, "question": 原題}` |
| `prompt` | 字典的兩個鍵剛好對上模板的 `{context}` 和 `{question}` |

為什麼需要 `question` 那條路？因為問題走進 `context` 那條路以後就被換成資料了，AI 還需要知道原本的題目是什麼。

**5. Prompt 裡防止亂編的規則**

```
只能根據下面的資料回答。資料裡沒有的，就說「這個問題我不確定……」，不要自己編。
```

### 預期結果
- 「我要怎麼付錢？」→ 回答 7-11 門市取貨付款。
- 「粉底拆開用過了還能退嗎？」→ 回答已拆封的個人衛生用品不適用七天猶豫期，但瑕疵或寄錯仍可辦理。
- 「你們有賣電視嗎？」→ 應該回答不確定、請聯絡客服。**如果 AI 自己編了答案**，就是小模型沒照規則，可以拿來跟學員討論。

### 動手改改看
1. 在 `faq.md` 加一題「有沒有發票？」，重新執行，問問看。
2. 把 `k=2` 改成 `k=5`，看回答有沒有變好或變差。
3. 換幾種問法測試搜尋，例如「多久會到」、「寄到哪裡拿」，看找到的段落對不對。

## 步驟 5：step5_agent.py —— 完整的客服 Agent

### 這一步的目標
把前面學的全部組起來：Agent 自己判斷要查 FAQ、找商品、查價格還是查運費，而且記得之前的對話。

### 執行方式
```powershell
python src\step5_agent.py --demo   # 自動跑一輪示範問題
python src\step5_agent.py          # 自己輸入問題聊天
```

聊天模式中：輸入 `new` 換一個新顧客（記憶清空），輸入 `exit` 離開。

### 架構

```
顧客提問 → Agent（Gemma 4）判斷
             ├─ 規則、流程     → search_faq          （FAQ 向量庫）
             ├─ 找商品、推薦   → search_products     （商品向量庫＋混合搜尋）
             ├─ 價格、庫存     → get_product_detail  （查商品資料）
             ├─ 運費           → get_shipping_info   （查設定）
             └─ 附近的 7-11    → search_711_store    （全台 7,380 家門市，地址精準比對）
           → 整理後回答
```

**為什麼找門市不用向量搜尋？** 地址要的是精準比對：顧客說「學勤路」，就要找學勤路上的門市，「意思相近的路名」沒有意義。所以 `search_stores`（knowledge.py）把地址拆成縣市、行政區、路名三段來比對（路名 +3、行政區 +2、縣市 +1 分）。**不是所有搜尋都要用 AI，選對工具最重要。**

它還會檢查行政區對不對：顧客說「樹林區學勤路」，但學勤路上的 7-11 都在三峽區，工具就會提醒模型請顧客確認地址。

結果會**分組**回傳：「最推薦：在學勤路上的門市」和「樹林區的其他門市」。一開始是混在一起列 5 家，實測模型有時會漏掉最符合的學勤門市；分組並標明「一定要列出這一組」以後就穩定了。**給模型的資料整理得越清楚，它越不容易出錯。**

### 程式解說

**1. 兩個知識庫（knowledge.py）**

| 知識庫 | 資料來源 | 內容 | 一段 = |
| --- | --- | --- | --- |
| FAQ 庫 | `data/faq.md`（網站的退換貨說明、服務條款） | 店家規則，共 18 題 | 一題 |
| 商品庫 | `data/products.json`（網站上的 63 個商品） | 名稱、分類、規格名稱、說明 | 一個商品，`metadata` 記住 `product_id` |

這兩個檔案都是用 `scripts/sync_from_website.py` 從 yuchingmakeup.com 同步下來的真實資料。它會讀取「全部商品」頁面，再一個一個打開商品頁，把網頁裡的商品資料（名稱、敘述、每個規格的價格和庫存）抓下來。商品有更新時，重新執行一次就好。

**為什麼價格和庫存不放進向量庫？** 因為它們隨時在變。向量庫裡存的是建立當時的內容，庫存賣完了它還是會說有貨。所以價格、庫存要用工具即時查。

分成兩個庫，是為了讓 Agent 好判斷，也避免搜尋退貨規則時跑出一堆商品。

**2. 四個工具**

```python
@tool
def search_faq(question: str) -> str:
    """查詢店家的規則和流程，例如：下單方式、付款、取貨……"""
    results = faq_store.similarity_search_with_score(question, k=2)
    hits = [doc.page_content for doc, score in results if score >= MIN_SCORE]
    ...
```

- **相似度門檻 `MIN_SCORE = 0.4`**：分數太低的不要，避免拿不相關的資料硬回答。這個數字是實測出來的：

  | 問題 | 最像的 FAQ | 相似度 |
  | --- | --- | --- |
  | 運費怎麼算 | 運費怎麼算？ | 0.86 |
  | 我要怎麼付錢 | 運費怎麼算？／服務條款：四、付款與取貨 | 0.66／0.52 |
  | 沒去取貨會怎樣 | 退換貨說明：五、未取貨 | 0.50 |
  | 東西壞掉可以換嗎 | 退換貨說明：四、商品瑕疵、寄錯或缺件 | 0.50 |
  | 可以用信用卡嗎 | 服務條款：四、付款與取貨 | 0.49 |
  | 拆開用過的可以退嗎 | 服務條款：六、退換貨 | 0.47 |
  | 你們有賣電視嗎（無關） | 運費怎麼算？ | 0.39 |

  相關問題的最高分都在 0.47 以上，無關的約 0.39，所以門檻設 0.4。差距不大，資料更新或換模型後要重新測一次。

```python
@tool
def search_products(need: str, max_price: int | None = None) -> str:
    """依照顧客的需求找商品，回傳商品編號、說明、即時價格和庫存。

    need：顧客的膚質、用途或想要的類型……不要把預算、性別、價格寫進 need。
    max_price：顧客的預算上限（新台幣，整數）。顧客有提到預算才填。
    """
    results = hybrid_search(product_store, need, k=4)
    ...
```

這個工具做這幾件事：

1. **混合搜尋把所有商品排好順序**（說明見下方），名稱完全一樣的商品只留一個（網站上有些商品重複上架）。
2. **即時讀取價格和庫存**：從商品資料（正式版是資料庫）讀出最新的價格庫存，附在結果裡。注意這跟「價格不放進向量庫」不衝突：向量庫裡只有名稱和說明，價格是**查詢當下**才去讀的。
3. **有預算時，用程式篩選**：分成「預算內的候選」和「最相關但超出預算的商品」兩組，都交給模型，由模型判斷哪個真的適合。
4. **預算內只留「有命中關鍵字」的商品**：實測問「500 元內的防曬」，預算內真正跟防曬有關的只有 3 個，以前會把第 4 名的面膜湊進來。湊數的商品關鍵字命中都是 0，所以有命中的才算候選（都沒命中時才退回用分數排）。

- **混合搜尋（`hybrid_search`，寫在 knowledge.py）**：總分 = 意思相似度 + 0.3 × 關鍵字重疊比例。
  1. 先用意思搜尋找出 6 個候選。
  2. 把問題和商品說明都切成「每兩個字一組」（例如「乾肌保濕」→ 乾肌、肌保、保濕），算有幾組相同。
  3. 加總後重新排序，取前 k 個。

**為什麼要加 `max_price`？這是實測踩到的問題**（早期用 8 個範例商品開發時遇到的，表格裡的乳液、卸妝油是範例商品）：

顧客問：「我是皮膚乾燥的男士，有什麼適合我的商品？希望 500 元以內。」

| 版本 | 結果 |
| --- | --- |
| 沒有預算參數 | 推薦了 680 元的乳液和 580 元的**卸妝油**，完全沒提超出預算 |
| 加了參數，但只回傳「預算內的商品」 | 預算內只有油性肌用的化妝水，模型覺得不對，結果**編造了兩個不存在的商品** |
| 加了參數，兩組都列出來（現在的版本） | 連跑 3 次都正確：說明化妝水不適合乾燥肌，推薦乳液和乳霜並標明超出預算 |

> **教學重點：AI 和程式各做擅長的事**
> - **數字比較交給程式**：「680 是否大於 500」這種事，小模型常常出錯，程式永遠不會錯。
> - **語意判斷交給模型**：「控油化妝水適不適合乾燥肌」這種事，程式很難寫規則，模型看說明就懂。
> - **給模型正確的選項**：只丟給模型一個不適合的商品，它會想辦法「生出」答案，就容易亂編。把真正適合的選項也一起給它，它就會選對。

**卸妝油為什麼不見了？** 沒有特別寫規則擋它，而是兩個改變一起發揮作用：
1. 預算不再寫進搜尋字串（以前是「皮膚乾燥 男士 500元內」，現在是「乾燥肌 男士」），搜尋變準了。
2. System prompt 要求「推薦前先判斷是否真的符合需求，寧可只推薦一個，也不要硬湊」。

也試過用相似度門檻擋，但卸妝油在不同問題的分數差很多（0.44～0.61），甚至會比另一題的正確答案還高，沒辦法用一個固定數字擋掉。這種「合不合適」的判斷，交給模型比較好。

**為什麼要混合搜尋？這是實測踩到的問題**（早期用 8 個範例商品開發時遇到的；換成 63 個真實商品後，又調整了候選數量，見教學建議的「坑 5」）：

只用意思搜尋時，「乾肌保濕」的結果是：

| 商品 | 意思相似度 | 關鍵字重疊 | 混合總分 |
| --- | --- | --- | --- |
| 清爽防曬乳 | **0.668**（第 1） | 0 | 0.668 |
| 玻尿酸保濕乳液 | 0.666 | 0.33（有「保濕」） | **0.766**（第 1） |
| 神經醯胺滋潤乳霜 | 0.652 | 0 | 0.652 |

防曬乳和保濕乳液只差 0.002，順序幾乎是隨機的。結果顧客問「那第一個多少錢？」，Gemma 4 查成了防曬乳的價格。

一開始試著改 system prompt 也沒用，**問題的根源在搜尋，不在模型**。加上關鍵字分數以後，保濕乳液穩定排第一，連跑 3 次都答對。

> **教學重點：**
> 1. 意思搜尋（Embeddings）擅長找「意思像的」，但分數很接近時排序不可靠。
> 2. 關鍵字搜尋擅長「字面上精準」。兩個一起用，互相補強。
> 3. 出錯時先找出是哪一站出問題（搜尋？模型？prompt？），再對症下藥。

- **為什麼不用 MMR？** 一開始用的是 MMR（`max_marginal_relevance_search`，挑「相關又不重複」的結果），但它的預設參數 `lambda_mult=0.5` 太重視「不重複」，反而把最該推薦的保濕乳液擠掉了。商品數量少時，混合搜尋比較合適。MMR 留作練習題。
- docstring 寫清楚每個參數該填什麼、**不該填什麼**（「不要把預算寫進 need」），模型才會正確地把預算放進 `max_price`。

```python
@tool
def get_product_detail(product_id: str) -> str:
    """用商品編號（例如 P001）查詢即時的價格和庫存……"""
```

- 這裡是讀同步下來的 `products.json`。要做到「後台一改價格，客服立刻知道」，可以改成直接查網站的 PostgreSQL 資料庫（記得用唯讀帳號）。工具裡面怎麼實作，AI 不在乎，它只看 docstring。
- 真實商品有多種規格（例如不同期限、容量），工具會把每個規格的價格和庫存分別列出來。
- 商品編號是網站上的代號（例如 `cmuns8as3yr0b`），就是商品頁網址最後那一段。

**3. System prompt 的規則**

每一條都有原因：

| 規則 | 原因 |
| --- | --- |
| **需要資料時直接呼叫工具，不要先說「我幫您查一下」** | 實測踩雷（見下方） |
| 規則問題用 search_faq，運費用 get_shipping_info | 告訴 AI 哪種問題用哪個工具 |
| 顧客提到預算，就填進 max_price，不要寫進 need | 數字交給程式篩選，搜尋字串保持乾淨 |
| 「第一個」指的是你回答給顧客看的清單，用 get_product_detail 查 | 避免 AI 用工具結果的順序去對 |
| 推薦前先判斷是否符合需求，寧可少推薦也不要硬湊 | 避免推薦不相關的商品（例如卸妝油） |
| 預算內沒有符合的，要照實說，再介紹超出預算的選擇 | 避免硬推不適合的、或亂編商品 |
| 價格、庫存、運費一定要用工具查 | 避免 AI 憑印象報錯價格 |
| 查不到就請顧客問真人客服 | 避免亂編 |
| 不誇大商品功效 | 化妝品法規禁止宣稱療效 |
| 不談論其他顧客的資料 | 隱私 |

> **實測故事：只說不做的客服**
> 第一版 prompt 只寫「用 search_faq 查」這類規則。結果 Gemma 4 每一題都回答「好的，我馬上幫您查詢！請稍等～」，**然後就結束了，一個工具都沒呼叫。**
> 加上第一條「直接呼叫工具，不要先跟顧客說我幫您查一下」以後，四題都正確使用工具。
> 這是小模型很常見的毛病：它學到了客服「講話的樣子」，卻忘了真的去做。

**4. 記憶**

```python
agent = create_agent(..., checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": thread_id}}
agent.invoke({...}, config)
```

- `checkpointer`：對話紀錄本。每次提問時，LangChain 會自動把同一本紀錄裡的舊對話一起送給 AI。
- `thread_id`：紀錄本的名字。同一個名字 = 同一段對話。
- 示範的第二題「那第一個多少錢？」就是在測記憶：AI 要記得上一題推薦了哪些商品，才知道「第一個」是哪個。
- 輸入 `new` 會換一個 `thread_id`，等於換一本新的紀錄本，AI 就不記得之前的對話了。

**5. 印出 Agent 用了哪些工具**

`ask()` 函式會把這一輪 AI 呼叫的工具印出來，例如：

```
   （呼叫工具：search_products {'need': '卸妝'}）
   （呼叫工具：get_product_detail {'product_id': 'cmuns8as3yr0b'}）
```

教學時非常好用，學員可以直接看到 Agent 的「思考路線」。

### 預期結果（示範模式）

| 問題 | 預期用到的工具 | 預期回答重點 |
| --- | --- | --- |
| 有沒有適合乾肌的保濕產品？ | search_products | 推薦 JYUNKA 玻尿酸面膜、瑪琍嘉蘭護理霜、雪肌精極潤型等，附價格和庫存 |
| 那第一個多少錢？還有貨嗎？ | get_product_detail | 說出第一個商品的價格和庫存（記得上一題） |

| 拆開用過的可以退嗎？ | search_faq | 已拆封的不適用七天猶豫期；瑕疵、寄錯 7 天內可換貨或退款 |

商品資料會隨網站更新，推薦的商品、價格、庫存不一定跟上表完全一樣。
